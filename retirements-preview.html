Support for Azure Linux with OS Guard in Azure Kubernetes Service will end on December 10, 2026. Azure Container Linux is the replacement for Azure Linux with OS Guard (preview). Starting on December 10, 2026: - Users won’t be able to create new Azure Linux with OS Guard (preview) node pools. - AKS won’t produce new node images for affected node pools. - Existing node pools won’t receive security patches. On March 10, 2027, AKS will remove the Azure Linux with OS Guard node images. After the images are removed, scaling and remediation operations, including reimage and redeploy operations, will fail for affected node pools. You can use either of the following migration options: - Migrate an existing Azure Linux with OS Guard node pool in place by following the Migrate nodes to Azure Container Linux for Azure Kubernetes Service documentation. This operation preforms a standard node image upgrade. - Alternatively, create a new Azure Container Linux node pool, migrate and validate workloads, and then delete the Azure Linux with OS Guard node pool. Follow Add Azure Container Linux node pools and remove existing node pools. For other available options, see the AKS node operating system. If you have questions, get answers from community experts in Microsoft Q&A or AKS GitHub Repository. If you have a support plan and need technical help, create a support request.

Beginning September 30, 2027, support for the pod name dimension on the following Azure Monitor platform metrics is retiring, and these metrics are transitioning to aggregate pod counters: - Number of pods by phase (kube_pod_status_phase) - Number of pods in Ready state (kube_pod_status_ready) After this change: - Metric names remain unchanged. - Aggregate pod counts remain available. - Namespace-level monitoring scenarios remain supported. - The pod name dimension will no longer be available for filtering, grouping, or alerting. During the deprecation period, AKS will maintain both the existing and the new aggregate implementations. Both are populated with data, existing monitoring experiences will continue to function, and you will have at least one year of historical data in the aggregate implementation before retirement. You may be affected if any dashboard, workbook, alert, automation, or monitoring workflow: - Uses kube_pod_status_phase or kube_pod_status_ready and filters on the pod name dimension. - Splits or groups results by the pod name dimension. Recommended action: - If you use aggregate pod counts, no action is required. - If you use the pod name dimension, update dashboards, alerts, workbooks, and automation before September 30, 2027. For pod-level monitoring and troubleshooting, we recommend using Azure Monitor Managed Prometheus and Kubernetes-native pod metrics. The Azure Key Vault Secrets Provider Extension for Azure Arc-enabled Kubernetes will be retired on October 9, 2027. Customers currently using the extension should plan to migrate to the Azure Key Vault Secret Store Extension before the retirement date. The Azure Key Vault Secret Store Extension provides equivalent functionality for accessing and synchronizing secrets from Azure Key Vault for workloads running on Azure Arc-enabled Kubernetes clusters. In addition, the Azure Key Vault Secret Store Extension includes enhancements such as support for offline access to secrets and authentication using workload identity federation, enabling applications to access Azure Key Vault without storing long-lived credentials on the cluster. After retirement, the Azure Key Vault Secrets Provider Extension will no longer receive new features, bug fixes, security updates, or technical support. Migration guidance is available to help customers transition their workloads and configurations to the Azure Key Vault Secret Store Extension ahead of retirement.
